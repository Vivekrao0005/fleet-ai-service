What it does

Four capabilities, each backed by a dedicated tool function that the LLM selects via structured intent classification.

🚘 Vehicle Status

Look up any vehicle by ID. Get make, model, mileage, current location, and rental status in one query.

📊 Utilization Analytics

Count, average, and filter vehicles by utilization. Deterministic math — count and revenue answers bypass the LLM entirely.

🔧 Maintenance Flags

Surface vehicles in maintenance, their severity, estimated cost, and open tickets. Filter by status or vehicle type.

📦 Transfer Requests

Identify underutilized vehicles and recommend relocations. Every transfer goes through a human approval gate before execution.

How it works

A two-call LLM pattern. The first call classifies intent into structured JSON. The second generates a natural-language answer from real data. Numeric queries (count, average, revenue) skip the second call and return deterministic results.

Database schema

Five PostgreSQL tables. All data is synthetic — 20 US locations, 200 vehicles with fabricated VINs, and realistic utilization patterns.

TablePurpose
locations20 US cities with airport codes, demand scores per vehicle type (sedan, SUV, truck)
vehicles200 vehicles — ID, VIN, make/model/year, type, status, mileage, utilization %, daily revenue
maintenance_recordsRepair tickets with severity (LOW–CRITICAL), status, estimated cost, notes
utilization_historyMonthly snapshots — utilization %, rental days, available days per vehicle
transfer_requestsAI-recommended relocations with approval status, audit trail, and human approver field

Approval gate

The AI can analyze the fleet and recommend transfers, but it cannot unilaterally move a vehicle. Every relocation request follows this workflow:

AI recommends → PENDING_APPROVAL → Human approves → APPROVED → IN_TRANSIT → COMPLETED

This is enforced at the database level, not the application layer. The transfer_requests table has:

  • A CHECK constraint on status limiting values to the six valid states
  • An approved_by column — must name a human before status can change to APPROVED
  • requested_at, approved_at, completed_at timestamps for a full audit trail
  • A CHECK (from_location_id <> to_location_id) to prevent no-op transfers

Because the constraint lives in PostgreSQL, it is enforced regardless of which client writes to the table — the API, a migration script, or a direct SQL session.

REST endpoints

MethodPathDescription
POST /api/ask Send { question, history } — returns { answer, tool? }
GET /api/tools/vehicle/:id Direct vehicle lookup by ID (bypasses LLM)
